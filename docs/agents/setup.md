# Setup

The setup screen (`window/Setup.js`) and its steps.

- The setup screen (`window/Setup.js`) changes the system only after the user presses y on a step, and it never runs an install command without a terminal the user sees (ADR 0007). The Packages step (kind `install`, required) lists what a stock Omarchy lacks (`missingPackages`: a JDK 21+, `qt6-websockets`, `suwayomi-server-bin`) and, after y, runs `omarchy-launch-floating-terminal-with-presentation "<command>"` with `omarchy-pkg-add <arch packages> && omarchy-pkg-aur-add suwayomi-server-bin`, only the missing parts; the step shows that command, and the user types the sudo password in the terminal. The launcher returns at once, so `Setup.installing` holds while the job succeeded and packages are still missing, and `SetupView` rechecks every 5 s. While Suwayomi-Server is missing, the probe asks `yay -Si suwayomi-server-bin` for its version (`aurSuwayomi`, `?` when yay cannot tell; the probe's `$5` skips it on rechecks); a version newer than `Session.APPROVED_SUWAYOMI` turns the prompt into a warning that still installs on y. `reduce` keeps the first check's `aurSuwayomi` across rechecks, which skip the query, and `yay` gets 20 s (`timeout`). A drive needs only stubs on `PATH`: a `java` that reports 17, and an `omarchy-launch-floating-terminal-with-presentation` that records its argument and rewrites the `java` stub to 26 three seconds later, in the background, so "Installing in the terminal…" shows before the 5 s recheck turns the step done. After a cancelled or failed install the recheck keeps running while Setup shows; Enter offers the terminal again. Each step detects "done" from a fresh check, so a rerun changes nothing. The sync folder lives in meta `miharchy.syncFolder`. A step's scripts address files through `$HOME`, so a test run with `HOME=<scratch>` (plus `JAVA_TOOL_OPTIONS=-Duser.home=<scratch>` for the JVMs) touches nothing real; `systemctl --user` ignores `HOME`, so stub it.
- Setup opens once for optional steps that became due and records them in meta `miharchy.setupOffered` (`Setup.unoffered`, `SetupView.offer`), so a skipped step stays quiet until its state changes. Only a window started with no open target makes that offer (`Setup.offersOnStart`): a peek, an `open-chapter` or an `open-updates` window opens something else, so Setup would never show and the offer would be lost (#230). The next plain launch, or a restart with `Q`, makes it.
- The Setup step "Sync helper" builds it after `y`: it copies the plugin's `sync/` (without `build/`, `.gradle/`, `.kotlin/`) to `~/.local/share/miharchy/sync-src/`, runs `./gradlew --no-daemon installDist` there, and swaps the install into `~/.local/share/miharchy/helper/` only when the build succeeds. `helper/source.sha256` is the fingerprint of the sources it was built from: sha256 over the sorted `sha256sum` lines of every file in `sync/` except those three folders (the `FINGERPRINT` script in `window/Setup.js`). The probe fingerprints the plugin's `sync/` the same way; a mismatch shows the step "out of date". Keep build output (`helper/`, `sync-src/`) apart from sync state (`sync/`).
- The Setup step "App launcher entry" writes `~/.local/share/applications/miharchy.desktop` (`Setup.desktopEntry`), with `Exec` on the plugin's `window/miharchy` and `Icon` on `icons/miharchy.svg`. The icon pack and its usage table are in `icons/` (`icons/README.md`); the bar mark draws `plugin/MiharchyIcon.qml`. The Omarchy launcher reads XDG desktop entries. The probe compares the file byte for byte, so a moved plugin shows the step to do again.
- The Setup step "Peek key" appends `o.bind("SUPER + M", "Miharchy peek", "'<window>/miharchy' peek")` (`Setup.peekLine`, the same path as the launcher entry) to `~/.config/hypr/bindings.lua`, Omarchy's file for personal binds. It is the only step that writes into the user's Hyprland config, and it writes once: a line that runs `miharchy peek` on any key and is not a Lua comment counts as done (`HAS_PEEK_KEY`), so a bind the user moved stays as it is. A taken `SUPER + M` (`hyprctl binds -j`, modmask 64), a `hyprctl` that cannot list the binds, or a missing `bindings.lua` leaves the line in the step's output to paste. It never writes `bindings.conf`. Hyprland reloads the file itself. A test stubs `hyprctl` and runs with `HOME=<scratch>`.
- The Setup step "Phone backups" (kind `check`: the user acts on the phone, Enter checks again) is done once a phone backup (a `*.tachibk` that is not `miharchy-*`) sits at the top of the sync folder, where the sync reads it. The sync folder lives in server meta, so `Setup.phoneProbeCommand` runs as its own job (`phones`) after the server reply, not in the probe; `Setup.offers` waits for it, so the one-time offer can include the step. While the step is `todo` (or still `checking`) and Setup shows, a 15 s timer runs the check again. The check never starts over a y/n prompt or the folder field: starting any job clears `confirm` and the message, so a recheck would cancel "Build the sync helper now?" under the user. Only a folder named `autobackup` below the sync folder means Mihon's storage folder was shared: the step says to set the sync folder to that folder. A drive needs the server step done: put a `systemctl` stub first on `PATH` (`is-enabled` → enabled, else active), copy `server/miharchy-server.service` into `$RUN/home/.config/systemd/user/` and, from a first step, into `$RUN/app/server/` (`drive.sh` rebuilds `$RUN/app`, and the probe compares the plugin's unit beside `window/`), then call `setupView.check()`.
- The "Phone backups" step pairs with Syncthing while no phone backup has landed. After the phone check, `SetupView` runs `Setup.syncthingProbeCommand` (job `syncthing`): it reads the GUI address and API key from `~/.local/state/syncthing/config.xml` (or `~/.config/syncthing/`), asks `system/status`, `config/folders` and `cluster/pending/{devices,folders}` with `curl` and `jq`, and writes this desktop's ID as a QR code (`qrencode`) to `$XDG_RUNTIME_DIR/miharchy/syncthing-id.png`. "installed" means Syncthing wrote its config, so it was started once. With no config, `y` opens Omarchy's terminal on `omarchy-pkg-add syncthing && systemctl --user enable --now syncthing`; installed but not answering, on `systemctl --user enable --now syncthing` (the status carries `command`, and `SetupView` passes the confirmed step's command as `install`, so `runCommand("phoneBackups")` opens the terminal instead of accepting). The sync folder counts as paired when a Syncthing folder with that path (after `~` and `realpath -m`) is shared with another device; then the step skips pairing. `Setup.pairing` picks what `y` accepts: the pending device, or the one offered folder, or the one named `autobackup` among several; with several and none so named, the step points to Syncthing's page instead (no picker). `status` carries the prompt and the QR path, so the y/n line and the image follow the state. The accept (`runCommand("phoneBackups")`) POSTs `config/devices` and `config/folders` (send and receive, at the sync folder path, shared with the offering device). It writes Syncthing's config, so only after `y`, like the peek key. Tests and drives use a stand-in Syncthing: `window/tests/syncthing.test.js` runs a stub HTTP server in the test; a drive runs `.claude/skills/verify-miharchy/scripts/syncthing-stub.js` on its own port, started with `setsid` and stopped by its PID (never `pkill -f`, which matches its own shell), with a `config.xml` in `$RUN/home` pointing at it. Never point either at the real Syncthing. Once Syncthing knows a device besides this desktop (`knowsPhone`) but no folder share has arrived, the step asks for the share instead of showing the QR code again. Known limit: a GUI with `tls="true"` needs `https`, so the check reads it as not answering.
