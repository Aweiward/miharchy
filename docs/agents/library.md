# Library, downloads, migrate and history

Library updates, categories, download deletion, Migrate, History and the library check.

- A library update is Suwayomi's `updateLibrary` (`Updates.checkPayload`). With no categories (`u` on Updates, `u` on the Library's All, and the server's schedule) the server applies each category's `includeInUpdate`, the rule of Mihon's `LibraryUpdateJob`: once one category is INCLUDE, only included ones update, and a manga in any EXCLUDE category never does. With category ids (`u` on any other Library category, Default is id 0) it updates every manga in them, whatever the flags. `u` on Categories cycles UNSET, INCLUDE, EXCLUDE. `d` cycles `includeInDownload` the same way, which Suwayomi reads by the same rule when it auto-downloads new chapters (the Settings row `autoDownloadNewChapters`).
- Updates follows a library update through `libraryUpdateStatusChanged` while the view shows (`Updates.LIVE_QUERY`), the server's scheduled runs too; its results carry only the counts, so the list reloads when a run ends and brings the last-checked time and skip filters. A run opens with an all-zero result before it counts the library, so `u`'s "checking" waits past it. The download queue follows `downloadStatusChanged` while its overlay shows or anything waits in it (`Downloads.LIVE_QUERY`): the first result is the whole queue, later ones change it, and a finished download leaves it. While the subscription runs, download mutation replies leave the queue alone: their status can be older than the last result.
- The default category (Settings, meta `miharchy.defaultCategory`: `ask`, `0` for Default, or a category id) is the window's: GraphQL `updateManga(inLibrary: true)` ignores Suwayomi's own `default` category flag, which only its REST add applies. When the manga detail adds a manga, `shell.qml` `addedToLibrary()` moves it to exactly that category (none for Default), or opens the detail's categories picker for `ask`, as Mihon. A manga that left the library keeps its old categories on the server until then.
- Suwayomi never deletes a download on its own, so the window runs Mihon's delete group: after reading (the reader, `Reader.deleteTarget`) and after a mark read (`shell.qml` `deleteRead`). Both go through `Downloads.autoDeletePayload`, which reads the chapters from the server first: only read chapters on disk go, bookmarked ones only when allowed, and never one of a manga in a category whose meta `miharchy.keepDownloads` is `"true"` (`p` on Categories).
- Migrate (`window/Migrate.js`) follows Mihon's `MigrateMangaUseCase`: every target chapter up to the highest chapter number read on the old manga is read, a bookmark moves to the chapters with its number, and the target gets exactly the old categories and reading mode, and the old manga's tracks unless `t` on the confirm leaves them out: `bindTrackRecord` copies each track record to the target in the server's database (the old manga keeps its own, as in Mihon), never calling the tracker, in the same write as the rest. It reads the old manga from the server's database only, so a manga whose source is gone still migrates. The target write goes first; only after it succeeds does the old manga leave the library (Migrate, not Copy) and lose its downloads.
- A migrate batch (`MigrateView.begin`: `M` on Browse's Sources after the source is picked, or `M` on the library check) gives each manga its targets with `Migrate.withTargets`: a source named like its own (`Migrate.key`; while its own is installed, only in its language, so MangaDex (EN) never goes to MangaDex (FR)), then the pinned sources (`Browse.pinned`, passed in from `browseView.prefs`) in pin order, never its own. When no manga has any, the user picks one source for all (`Migrate.withTarget`, step `to`; a manga already on it gets none). Each batch row is one GlobalSearch group: a search with no match at `Migrate.THRESHOLD` (`propose`), a failure or a timeout swaps the group for the manga's next target, so `due` starts it again; the first match stops it. One request at a time, as Mihon. A stalled manga (`LibraryCheck.migrateList`, any of its problems stalled) holds its match (`held`) until `checkPayload` fetches the match's chapters; it takes the match only when their highest number beats the old manga's (`HIGHEST_QUERY`, `highestNumberedChapter`), else it moves on (a failed or timed-out check too, `Migrate.expired`, or on the last target it waits for `r`), and with no target left the row says "No source has more chapters." `h`/`l` step through the last searched source's results only.
- Suwayomi cannot delete history: only a `lastPageRead` save moves `lastReadAt`. So History hides instead, never touching read state. An entry hides while its `lastReadAt` is at or below the manga meta `miharchy.historyHiddenAt` (remove) or the global meta `miharchy.historyClearedAt` (clear all). Both hold a server `lastReadAt`, so opening the chapter again brings it back. Backups still carry the full history.
- The library check (`GLOSSARY.md`) is `window/LibraryCheck.js`, wired by `LibraryCheckView.qml`: a screen like Setup (`root.view === "check"`, command `view.check`: the palette, `!` on the Library, Enter on the Settings action row `libraryCheck`), not a view. Each load (the screen showing, `r`, Settings showing for the row's count) sends one `LibraryCheck.QUERY` and derives every problem from it; nothing but dismisses is stored. Times are normalized to ms: `chaptersLastFetchedAt` and `fetchedAt` come in seconds, `uploadDate` and `lastUpdateTimestamp` in ms. The kinds are the `KINDS` table, one reason per manga and kind. Update failed needs `lastUpdateTimestamp` after `chaptersLastFetchedAt`, that fetch over 14 days old, an installed source, and no skip by design (`updateStrategy` `ONLY_FETCH_ONCE`, or the server's `excludeUnreadChapters`, `excludeNotStarted` with no `lastReadChapter`, `excludeCompleted`); a `FAILED` entry in `libraryUpdateStatus.mangaUpdates` (server memory, lost on restart) only changes the reason. Duplicates compare `Migrate.key` of the titles (a title with no Latin letters or digits as written), equal or `Migrate.similarity` at 0.9 or more, over every pair after a length cut. Stalled reads the newest upload date, or the fetch time when it is 0, so a manga with no chapters is only "No chapters". `x` writes manga meta `miharchy.checkDismissed`, `{ kind: ms }`, keeping the manga's other kinds (`dismissPayload`, one `setMangaMeta` per manga in one mutation); in the `X` list it removes them. Only a stalled dismiss lapses, when the newest chapter is newer than it. `space` keeps `selected` by problem key; `M` (`check.migrate`, routed in `shell.qml` to `MigrateView.startList`) migrates `LibraryCheck.targets` (the selection, else the group or row under the cursor) as a migrate batch, and the check loads again when it ends. Enter on an extension update row sends `Extensions.actionPayload(pkgName, "update")`.
- Enter on a duplicate row merges a pair: the row's manga and `others[0]`, so three copies take two merges. `LibraryCheck.MERGE_QUERY` reads both (source, read chapters, categories, tracks) into the prompt (scope `check-merge`: `j`/`k`, Enter keeps the copy under the cursor, Esc cancels). `mergeJob` hands the pair to `MigrateView.startWith(old, kept)`, the existing confirm and write. Every migration merges when its target is already in the library, whatever led there (the check's `M` and Enter, Browse's batch, a manga's `M`): `prepare` reads the target's `inLibrary`, `meta` and `trackRecords` from `TARGET_MUTATION`, and `Migrate.mergeInto` gives the job's `merge`, or null for a target outside the library, which keeps Mihon's plain Migrate exactly. In a merge, the target's own state wins (`Migrate.targetPayload`): no `clearCategories`, so it keeps its categories and gains the other's (it is in the library already, so no default category joins); the other's reading mode applies only when the kept copy has none; the other's tracks bind only on trackers the kept copy has no track on (`Migrate.movingTracks`). `plan` never unmarks, so the kept copy's read state only goes up. A copy whose source is missing cannot be kept (Migrate fetches the target from its source): the prompt marks it "source missing", the cursor starts on a copy that can be kept and `j`/`k` skip it (`mergeStart`, `mergeMove`); with both missing, the prompt says no copy can be kept and Enter does nothing. After the write the check reloads and the kept copy's detail opens, as after any single migration.
