# Sources and extensions

Browse, local manga, extension repos, source filters and settings, FlareSolverr.

- Core has the local source (#374, `core/README.md`): source 0 in `source.list`, answered by `Local.kt`, reading `localSourcePath` (blank means `<core data>/local`). The window gets the folder core reads from `storage.get` (`localFolder`; the shell keeps it, `Storage.localFolderOf`) for the empty-listing notice. It reads Mihon's layout: a folder per manga, a folder of images or a `.cbz`/`.zip` per chapter, `ComicInfo.xml` or `details.json`, `cover.jpg`. Browse lists it under Other whatever the languages (`LOCAL_SOURCE` in `window/Browse.js`), as Mihon's `GetEnabledSources`; global search, the languages panel and Migrate leave it out, as in Mihon. A local manga's detail has no download, download menu or delete keys (`Downloads.offered`). A backup carries local manga as Mihon does (`source` 0, `url` the folder name, chapter `url` `<folder>/<file>`), so the sync needs nothing special.
- Browse adds the Keiyoushi extension repo once per core and records that in meta `miharchy.repoPreset`, so a repo the user removes stays removed. Core reduces any repo address (the folder, `index.min.json`, `repo.json`, `index.pb`, `index.json`) to the repo's `index.json`, on add and on remove. The window removes a repo by the `indexUrl` core returns (`extensionRepo.remove`).
- A source's filters and settings are widgets its extension defines. `window/Widgets.js` parses both into one tree, edits it, and builds `source.search`'s `filters` and `source.setSetting`'s `key` and `value`; `WidgetPanel.qml` shows it. Filters address the source's full list by position, so hidden rows keep their place. A setting saves by its key. Core hands filters to the source only in `source.search`, so applying filters searches (`F` on a source); they live for the window's life and are never stored, as in Mihon. A setting saves at once (`S`), and `source.setSetting` answers with the source's settings read again. Enter on an installed extension opens its details (`Extensions.details`: version, language, its sources); Enter on a source there opens the same settings panel, which BrowseView draws over the Extensions screen. Core has no per-source enable switch, so the details have none. `u` updates one extension (`extension.update`) and `U` all that have an update (`extension.updateAll`).
- FlareSolverr is optional (#361, `core/README.md`). Core's host asks it to pass a Cloudflare challenge when `flareSolverrEnabled` is on. Setup's step starts it as a Docker container bound to `127.0.0.1:8191` and turns the setting on, with `flareSolverrAsResponseFallback`, through the Settings row (`Setup.savePayload`). The step is done when the container runs and core's `settings.get` says `flareSolverrEnabled`. A source it cannot pass still fails with kind `cloudflare`, and every view says to turn FlareSolverr on (`Model.problem`). Manganato passes on its `www.nelomanga.net` mirror, at about 12 s a request, because its cookie never passes without the solver; on `www.natomanga.com` the extension's parser finds no manga in the solved page. Kagane still fails: its challenged request is not a GET. The step ran on the user's machine; `docs/spikes/cloudflare-solvers.md` compares FlareSolverr with Byparr.
- Setup runs FlareSolverr by digest (`FLARE_IMAGE` in `window/Setup.js`), never by a tag, so a reviewed commit names the exact image. To bump it, take the new release's tag from https://github.com/FlareSolverr/FlareSolverr/releases and run `docker buildx imagetools inspect ghcr.io/flaresolverr/flaresolverr:<tag>`. Copy the top `Digest:` line, the multi-arch index, not one platform's manifest. Put it in `FLARE_IMAGE` and the version in the comment above it. Setup reuses an existing `miharchy-flaresolverr` container, so a user gets the new image only after `docker rm -f miharchy-flaresolverr` and a rerun of the step.
- Some sources (AllManga for its pages, at times its manga details) run part of their site in a WebView. Core's extension host has no WebView, so such a request fails with kind `webview`. `Model.problem` names it by that kind in every view ("This source needs a WebView", #98; `Model.BLOCKED`), so Browse, the detail and the reader keep the reply's `kind` in their state. The download queue labels it "Source needs a WebView" (`Failure.js`). Core stores the Settings row "Server WebView (KCEF)" (`kcefEnabled`) but does not act on it, so the row carries only Settings' "does not use it yet" note.
