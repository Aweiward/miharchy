# Bar mark, popup and launcher

The shell side in `plugin/` and the launcher `window/miharchy`.

- The shell keeps running the mark's old code after `omarchy plugin update` until `omarchy-restart-shell` (omacom/omarchy#6981: its cache clear is a no-op, `typeof Qt.clearComponentCache` is `undefined`). The window is its own process and starts on the new code. To check what the mark runs, compare the shell's start time (`ps -o lstart= -p <pid>`) with the update.
- The mark polls `Updates.UPDATES_QUERY` once a minute and when the popup opens. Choosing an update runs `window/miharchy open-chapter <mangaId> <chapterId>`. The launcher calls the running window's `miharchy` IpcHandler (`quickshell ipc -p window call miharchy openChapter ...`); with no window running, it starts one with `MIHARCHY_OPEN_CHAPTER` set. A second launch or an `open-chapter` focuses the running window: the launcher takes its instance pid from `quickshell list -j -p window`, finds that pid's address in `hyprctl clients -j` (every Quickshell window has class `org.quickshell`), and dispatches the focus `omarchy-launch-or-focus` uses. `window/miharchy peek` shows and hides a peek (`docs/agents/window.md`). `window/tests/launcher.test.js` runs the launcher against stub `quickshell` and `hyprctl`.
- The mark notifies about new chapters (Mihon's `LibraryUpdateNotifier`). Its poll (`Mark.listPayload`) also reads meta `miharchy.notifyNewChapters` (Settings row, on by default). A chapter is new when its id is above the highest update id the mark saw (`mark.top`); the first answer only sets it, so a start never floods, and a chapter marked unread again stays below it. `Mark.notifyCommand` runs `notify-send -A default=Open` detached; clicking runs `window/miharchy open-updates` (IPC `openUpdates`, or a new window with `MIHARCHY_OPEN_VIEW=updates`). Each monitor's bar polls on its own, so the script sends only when it creates the marker `$XDG_RUNTIME_DIR/miharchy/notified-<newest id>` (noclobber). Never send a real notification in a test: `plugin/tests/mark.test.js` puts a stub `notify-send` first on `PATH`. A sync or restore that imports manga with recent unread chapters notifies too.
- The mark syncs when a phone backup lands. Its poll also reads meta `miharchy.autoSync` (Settings row "Sync when a phone backup arrives", off by default) and `miharchy.syncFolder`. With both set and no sync running, each poll runs `Mark.phoneCheckCommand`: a `find` for the newest `*.tachibk` in the folder that is not `miharchy-*`, at least 30 s old (a file still arriving waits), and newer than the helper's `phone-baseline.tachibk` (no baseline: any). On a hit it calls `startSync()`, the same path as `s`. A failed or held sync moves no baseline, so the hit would repeat every poll: the mark keeps the last hit (`<mtime> <path>`) in memory as `lastTried` and tries each file once. A newer file, or the user's `s`, retries. Only that sync notifies (`Mark.syncNotification`): "Synced from the phone" with the count lines, "Sync held", or "Sync failed"; no changes sends nothing. Its marker is `notified-sync-<mtime digits>`, the same on every bar. Every bar runs the check, so the others lose the helper's lock; "A sync is already running." stays silent. A manual `s` notifies nothing; the popup line shows its result.
