# Bar mark, popup and launcher

The shell side in `plugin/` and the launcher `window/miharchy`.

- The shell keeps running the mark's old code after `omarchy plugin update` until `omarchy-restart-shell` (omacom/omarchy#6981: its cache clear is a no-op, `typeof Qt.clearComponentCache` is `undefined`). The window is its own process and starts on the new code. To check what the mark runs, compare the shell's start time (`ps -o lstart= -p <pid>`) with the update.
- The mark polls `Updates.UPDATES_QUERY` once a minute and when the popup opens. Choosing an update runs `window/miharchy open-chapter <mangaId> <chapterId>`. The launcher calls the running window's `miharchy` IpcHandler (`quickshell ipc -p window call miharchy openChapter ...`); with no window running, it starts one with `MIHARCHY_OPEN_CHAPTER` set. A second launch or an `open-chapter` focuses the running window: the launcher takes its instance pid from `quickshell list -j -p window`, finds that pid's address in `hyprctl clients -j` (every Quickshell window has class `org.quickshell`), and dispatches the focus `omarchy-launch-or-focus` uses. `window/miharchy peek` shows and hides a peek, and `window/miharchy peek-next` shows it on the next manga in Up next (`docs/agents/window.md`). `window/tests/launcher.test.js` runs the launcher against stub `quickshell` and `hyprctl`.
- The popup shows the first 3 manga in Up next (`Mark.UP_NEXT_LIMIT`) in a section above the updates, which keep their 10 rows. It loads them only when it opens (`loadUpNext`, `Mark.upNextPayload`: `UpNext.payload()` plus meta `miharchy.downloadedOnly`), never in the poll: every bar polls on its own and the reply is several MiB on a large library. `Mark.upNext` turns the reply into rows: the title, the next chapter, and a reason by `UpNext.list`'s `tier`: "p. 4 / 20" (`page + 1` / `pages`, the page alone without a count), "3 left" (`unread`), "new 2d" (age of `update`, hours under a day). While it loads, after a failure, or with Up next empty, the section is hidden and the popup looks as before; server errors stay with the notice line. `Mark.entries` puts both sections in one list under one cursor (`Mark.move`), "Up next" and "Updates" heading the first row of each; a manga may show in both. When the rows change under an open popup (Up next landing late, a poll), `Mark.follow` keeps the cursor on the same row by its launcher arguments, so Enter opens what the user chose; a cursor on the top row stays on the top row, the head of Up next once it shows. Enter or a click on an Up next row runs `window/miharchy peek-open <mangaId> <chapterId>`: it shows the peek as `peek-next` does and calls IPC `peekOpen`, or starts a window with `MIHARCHY_PEEK="<mangaId> <chapterId>"`. The window opens that chapter as a peek, with a new Catch-up count and a new next-key run (`docs/agents/window.md`).
- The mark notifies about new chapters (Mihon's `LibraryUpdateNotifier`). Its poll (`Mark.listPayload`) also reads meta `miharchy.notifyNewChapters` (Settings row, on by default). A chapter is new when its id is above the highest update id the mark saw (`mark.top`); the first answer only sets it, so a start never floods, and a chapter marked unread again stays below it. `Mark.notifyCommand` runs `notify-send -A default=Open` detached; clicking runs `window/miharchy open-updates` (IPC `openUpdates`, or a new window with `MIHARCHY_OPEN_VIEW=updates`). Each monitor's bar polls on its own, so the script sends only when it creates the marker `$XDG_RUNTIME_DIR/miharchy/notified-<newest id>` (noclobber). Never send a real notification in a test: `plugin/tests/mark.test.js` puts a stub `notify-send` first on `PATH`. A sync or restore that imports manga with recent unread chapters notifies too.
- The mark keeps sync health for the popup. With meta `miharchy.syncFolder` set, each poll runs `Mark.newestPhoneCommand` (the newest `*.tachibk` that is not `miharchy-*`, with no age or baseline filter) and runs `miharchy-sync health` when the answer changes, so a new phone backup is read with auto-sync off too; it also runs after each sync. The popup shows `Sync.healthPopupLine` in red: "Phone is behind" or "No phone backup for N days" (over 3 days, `QUIET_DAYS`), and nothing while all is well. `root.now` moves on each poll, so a phone that goes quiet shows without a new file. `drive.sh` does not run the mark; `plugin/tests/mark.test.js` runs the real `find`, and `window/tests/health.test.js` pins the line.
- The mark syncs when a phone backup lands. Its poll also reads meta `miharchy.autoSync` (Settings row "Sync when a phone backup arrives", off by default) and `miharchy.syncFolder`. With both set and no sync running, each poll runs `Mark.phoneCheckCommand`: a `find` for the newest `*.tachibk` in the folder that is not `miharchy-*`, at least 30 s old (a file still arriving waits), and newer than the helper's `phone-baseline.tachibk` (no baseline: any). On a hit it calls `startSync()`, the same path as `s`. A failed or held sync moves no baseline, so the hit would repeat every poll: the mark keeps the last hit (`<mtime> <path>`) in memory as `lastTried` and tries each file once. A newer file, or the user's `s`, retries. Only that sync notifies (`Mark.syncNotification`): "Synced from the phone" with the count lines, "Sync held", or "Sync failed"; no changes sends nothing. Its marker is `notified-sync-<mtime digits>`, the same on every bar. Every bar runs the check, so the others lose the helper's lock; "A sync is already running." stays silent. A manual `s` notifies nothing; the popup line shows its result.
