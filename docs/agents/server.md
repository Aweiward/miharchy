# miharchy-core

How the server runs, how Miharchy talks to it, and how its secret stays private. `core/README.md` covers the routes.

- miharchy-core is the only server (ADR 0009, ADR 0010, #373). It runs as the systemd user service `miharchy-core` (`core/server/miharchy-core.service`), from the build Setup puts in `~/.local/share/miharchy/core-app`. It listens on `127.0.0.1:4591` and keeps its data in `~/.local/share/miharchy/core` (mode 700).
- `~/.config/miharchy/core.json` holds `{ url, secret }`. Core creates it on its first start, born mode 600, and repairs the mode on each start. `MIHARCHY_CORE_CONFIG` and `MIHARCHY_CORE_DATA` point the window, the bar mark and core at other files; the verify skill uses them for a scratch core.
- Every request is `POST /api/<route>` with a JSON body and `Authorization: Bearer <secret>` (`window/Session.js`). There is no login, no refresh and no token on disk besides the secret. `Session.js` is a `.pragma library` module, and every view sends through `Session.send` (a route) or `Session.image` (a server image); none builds its own XHR. A payload with no `route` fails at once and logs `miharchy: refused …`.
- No secret goes on a command line: any user reads `/proc/<pid>/cmdline`. A script feeds a password, token or API key to its tool on stdin (`jq -R`, `grep -f -`, `curl -H @-`). `window/tests/setup.test.js` and `window/tests/syncthing.test.js` check it.
- Live updates (the download queue, Updates) come over a WebSocket on `/api/live`, with no subprotocol (`window/Live.js`, `window/LiveSocket.qml`; the `WebSocket` type is `qt6-websockets`, a Setup step, made at run time so the window loads without it). The first message is the secret, then one subscribe per topic. A wrong secret closes the socket with 4401. Each topic's first message is its whole state, so a reconnect misses nothing. The socket pings every 10 s. A closed or failed socket (a core restart) reconnects after 1, 2, 4, 8, then 15 s.
- Suwayomi-Server is no longer installed or started. Setup's move (`move.start`, `core/README.md`) reads an old install once, with the username and password from its `server.json`; that is the only code that still logs in to Suwayomi (ADR 0005). Setup's Stop Suwayomi step disables its `miharchy-server` unit and leaves the package and data.
- No URL carries the secret. QML `Image` cannot send an Authorization header. So every image from the server goes through `window/ServerImage.qml`: `Session.image` fetches the bytes with the secret, a `FileView` writes them to `$XDG_RUNTIME_DIR/miharchy/images/`, and the `Image` shows that file. `window/Images.js` keeps one copy per URL for the process: the first instance fetches, the others show the file at once, and a fetch in flight serves every instance that asks. A copy no instance holds stays idle until the idle copies pass `IDLE_BYTES` (128 MiB, about 50 MangaDex covers), oldest out first; the reader's pages (`keepIdle: false`) never idle, so a read keeps only the pages it shows. Each fetch writes a new file name, so Qt's pixmap cache, keyed by file URL, never shows old bytes for new ones; a copy older than `MAX_AGE` (10 minutes) is fetched again on the next hold, since a cover's URL does not change when the server refreshes it. A file leaves by being emptied (FileView cannot delete), and the reader's quit path empties every file still holding bytes (`Images.drain`). A window that crashes or is killed skips that, so each file name starts with the window's PID (`<pid>-<random>-<n>`), and a new window removes at start (`rm`, from `shell.qml`) every file whose process is gone, every file with no PID in its name, and every file older than the process now holding its PID (a reused PID; a minute's slack for clock steps). `Images.sweepCommand` lists the dir's regular files and the running processes' start times; `Images.sweep` picks the files. A running window's files always stay. `Model.serverImageUrl` decides what is the server's: an image from any other host loads as a plain `Image`, without the secret.
