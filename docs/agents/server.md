# Suwayomi-Server

How the server runs, how Miharchy logs in, and how its credentials stay private.

- Suwayomi-Server runs as the systemd user service `miharchy-server`, from `~/.local/share/miharchy/suwayomi` (mode 700), on `127.0.0.1:4590` with `ui_login` (ADR 0005). `server/miharchy-server` sets it up and is safe to rerun. `ui_login` reads the same `authUsername` and `authPassword` keys as `basic_auth`. Setup's server step shows "outdated" while `server.conf` still says `basic_auth` (an install from before ADR 0005); rerunning the script switches it and restarts the server.
- `APPROVED_SUWAYOMI` in `window/Session.js` is the newest Suwayomi-Server version token login has been checked against (ADR 0005); Suwayomi's next release reworks its auth. Setup and the bar mark read `aboutServer { version }` and warn about a newer server (`Session.versionWarning`); everything keeps working. The AUR package (#43) reads the same line for its `suwayomi-server-bin<=` dependency. To raise it, check token login on the new release (the verify-miharchy skill's scratch server, then the window and the sync helper), then bump the constant.
- Suwayomi rewrites its `server.conf` with mode 644, so the 700 folder is what keeps the password private.
- Each process logs in for itself: the window and the bar plugin through `window/Session.js`, the sync helper through `Desktop.kt`. The login (`login(input: {username, password})`) is the only request that carries the password, and it carries no token, since the server refuses a login from a request that already has a valid one. Every other request sends `Authorization: Bearer <access token>`. Without a valid token, GraphQL answers HTTP 200 with an `Unauthorized` error (`Model.reply` reads it as "unauthorized") and file routes answer 401. On either, the process refreshes once (`refreshToken(input: {refreshToken})`, which returns only a new access token), or logs in again when the refresh fails, and sends the request once more. Tokens live in memory only; `server.json` keeps `{url, username, password}`.
- `Session.js` is a `.pragma library` module, so each process holds one copy of the tokens, and a refresh or login in flight serves every request waiting on it. Every view sends through `Session.send` (GraphQL) or `Session.image` (server images); none builds its own XHR.
- No URL carries the credentials or a token. QML `Image` cannot send an Authorization header. So every image from the server goes through `window/ServerImage.qml`: `Session.image` fetches the bytes with the token, a `FileView` writes them to `$XDG_RUNTIME_DIR/miharchy/images/`, and the `Image` shows that file. Each instance owns its files and empties them when its image changes or it is destroyed. `Model.serverImageUrl` decides what is the server's: an image from any other host loads as a plain `Image`, without the token.
