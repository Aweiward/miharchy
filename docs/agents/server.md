# Suwayomi-Server

How the server runs, how Miharchy logs in, and how its credentials stay private.

- Suwayomi-Server runs as the systemd user service `miharchy-server`, from `~/.local/share/miharchy/suwayomi` (mode 700), on `127.0.0.1:4590` with `ui_login` (ADR 0005). `server/miharchy-server` sets it up and is safe to rerun. `ui_login` reads the same `authUsername` and `authPassword` keys as `basic_auth`. Setup's server step shows "outdated" while `server.conf` still says `basic_auth` (an install from before ADR 0005); rerunning the script switches it and restarts the server.
- `APPROVED_SUWAYOMI` in `window/Session.js` is the newest Suwayomi-Server version token login has been checked against (ADR 0005); Suwayomi's next release reworks its auth. Setup and the bar mark read `aboutServer { version }` and warn about a newer server (`Session.versionWarning`); everything keeps working. The AUR package (#43) reads the same line for its `suwayomi-server-bin<=` dependency. To raise it, check token login on the new release (the verify-miharchy skill's scratch server, then the window and the sync helper), then bump the constant.
- Suwayomi rewrites its `server.conf` with mode 644, so the 700 folder is what keeps the password private.
- Each process logs in for itself: the window and the bar plugin through `window/Session.js`, the sync helper through `Desktop.kt`. The login (`login(input: {username, password})`) is the only request that carries the password, and it carries no token, since the server refuses a login from a request that already has a valid one. Every other request sends `Authorization: Bearer <access token>`. Without a valid token, GraphQL answers HTTP 200 with an `Unauthorized` error (`Model.reply` reads it as "unauthorized") and file routes answer 401. On either, the process refreshes once (`refreshToken(input: {refreshToken})`, which returns only a new access token), or logs in again when the refresh fails, and sends the request once more. Tokens live in memory only; `server.json` keeps `{url, username, password}`.
- `Session.js` is a `.pragma library` module, so each process holds one copy of the tokens, and a refresh or login in flight serves every request waiting on it. Every view sends through `Session.send` (GraphQL) or `Session.image` (server images); none builds its own XHR.
- Live updates (the download queue, Updates) are GraphQL subscriptions over a WebSocket on `/api/graphql`, subprotocol `graphql-transport-ws` (`window/Live.js`, `window/LiveSocket.qml`; the `WebSocket` type is `qt6-websockets`, a Setup step, made at run time so the window loads without it). The token goes in `connection_init` as `{ Authorization: <access token> }`, bare: with `Bearer ` the server refuses the socket, and with no token it acks and then refuses each subscription with `Unauthorized`. `Session.token` hands the socket the process's token and renews a refused one. Measured on v2.3.2243: an open socket keeps delivering after its token expires (only `connection_init` is checked); a new socket with an expired token gets ack and then an `error` with `Unauthorized`, so LiveSocket renews and connects again; the server closes a socket silent for 30 s (`1001 Connection Idle Timeout`) and never pings, so LiveSocket pings every 10 s; subscription ids are global across all sockets, and a reused one closes the socket (`4409 Subscriber for <id> already exists`), so each subscribe takes a random id. A closed or failed socket (a server restart) reconnects after 1, 2, 4, 8, then 15 s. Each subscription's first result is the full state, so a reconnect misses nothing.
- No URL carries the credentials or a token. QML `Image` cannot send an Authorization header. So every image from the server goes through `window/ServerImage.qml`: `Session.image` fetches the bytes with the token, a `FileView` writes them to `$XDG_RUNTIME_DIR/miharchy/images/`, and the `Image` shows that file. `window/Images.js` keeps one copy per URL for the process: the first instance fetches, the others show the file at once, and a fetch in flight serves every instance that asks. A copy no instance holds stays idle until the idle copies pass `IDLE_BYTES` (128 MiB, about 50 MangaDex covers), oldest out first; the reader's pages (`keepIdle: false`) never idle, so a read keeps only the pages it shows. Each fetch writes a new file name, so Qt's pixmap cache, keyed by file URL, never shows old bytes for new ones; a copy older than `MAX_AGE` (10 minutes) is fetched again on the next hold, since a cover's URL does not change when the server refreshes it. A file leaves by being emptied (FileView cannot delete), and the reader's quit path empties every file still holding bytes (`Images.drain`). `Model.serverImageUrl` decides what is the server's: an image from any other host loads as a plain `Image`, without the token.
