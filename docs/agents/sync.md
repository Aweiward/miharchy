# Sync, backups and restore

The Kotlin helper in `sync/` and the window code that runs it (`Sync.js`, `Backup.js`, `Restore.js`).

- `miharchy-sync sync [--folder <dir>] [--dry-run] [--apply] [--json]` is the whole sync in one run. Without `--folder` it reads meta `miharchy.syncFolder` from the server, so the window and the popup start it the same way. It merges the newest phone backup in (none yet is fine), writes the desktop backup to the sync folder, and only then moves both baselines. A failure leaves the baselines alone, so the next sync retries.
- The merge reads a manga missing from the phone backup as removed and a missing chapter as unread, so an empty or partial backup (a fresh Mihon, another phone, chapters left out) reads as mass removal. The sync holds when the changes remove at least 5 manga that are also at least 10% of the desktop library, or mark at least 50 chapters unread (`holds` in `Merge.kt`). A held sync returns `held: true` before `apply`, the export and both baseline writes, like `--dry-run`; `--apply` runs it anyway. The window lists the changes and runs `--apply` on `y` (`sync-held` scope); the popup only says "Sync held" and never applies.
- Before a real sync moves the desktop baseline, it copies the old one to `pre-sync.tachibk` beside it (mode 600). "Undo the last sync" (palette) opens "Restore a backup" on that file. A sync overrides a desktop value only while it still equals the desktop baseline (`pick` and the `inLibrary` rule in `Merge.kt`), so that baseline holds everything a sync can remove, and the restore only adds.
- `miharchy-sync check <file>` prints the sources and trackers a backup needs and the server lacks (`validateBackup`) as one JSON line. `miharchy-sync restore <file>` restores the whole file (`restoreBackup`, without client data or server settings), prints one JSON line per `restoreStatus` change, and merges the file's source names into meta `miharchy.sourceNames`. The restore holds `sync.lock`, so it never overlaps a sync. It moves no baseline: the restore only changes the desktop library, so the next sync counts those changes as desktop changes (ADR 0002) and keeps them. The window's "Restore a backup" (`window/Restore.js`, `RestoreView.qml`, palette only) runs both through `Sync.helperCommand`.
- The helper reads `MIHARCHY_SERVER_JSON` like the window and the mark. Its state dir and its `server.json` fallback come from `user.home`, which Java takes from passwd, not `$HOME`. The helper refuses to run when `$HOME` and `user.home` name different folders (`homeMismatch` in `Main.kt`), so a harness that sets only one never reaches the real baselines. A test run sets both, through `.claude/skills/verify-miharchy/scripts/qs.sh env <helper> <args>`.
- Backups Miharchy writes to the sync folder are named `miharchy-<UTC yyyy-MM-dd_HH-mm-ss>.tachibk`, so names sort by time. The sync ignores them when it picks the phone backup (the newest other `.tachibk`). It writes through a temp file that does not end in `.tachibk`, then renames it, and keeps the newest three (only names of exactly that shape count). The backup leaves out Suwayomi's Default category, its client data and its server settings (the server password).
- Each desktop backup a sync writes carries the app preference `miharchy_backup` (`MARKER_KEY`), its own file name (ADR 0006). Mihon restores app preferences unfiltered and backs them up by default, so `restoredFrom` reads the last desktop backup the phone restored from the newest phone backup. "Create a backup" carries no marker. Suwayomi never sees it: the sync's restore into Suwayomi carries only manga (`restoreBackup` in `Desktop.kt`).
- **Sync health.** A sync stores `pending-since` in the state dir: the time of the first sync whose `restorable` list went from empty to non-empty, cleared when it is empty again (`pendingSince` in `Health.kt`). The phone is **behind** when `restorable` is not empty and at least 3 phone backups (`BEHIND_AFTER`; Mihon keeps 4) are newer than pending since. A phone backup's time comes from Mihon's name, `app.mihon_<local yyyy-MM-dd_HH-mm>.tachibk`, read in the desktop's time zone, else from its file time (`phoneBackupTime`). `miharchy-sync health [--folder <dir>]` prints one JSON line with every field: `phoneBackup`, `phoneBackupAt`, `desktopBackup`, `restored`, `markerMissing` (the phone backup has no app preferences at all, so no marker can come back), `restorable`, `byHand`, `pendingSince`, `behind`. It reads the newest phone backup, the newest desktop backup and `pending-since`, writes nothing and takes no lock. No phone backup or no desktop backup is a valid answer.
- "Create a backup" (palette, or its Settings row) runs `miharchy-sync backup <folder>` under `sync.lock`. It writes `miharchy-backup-<UTC>.tachibk` to the backup folder: Settings' "Backup folder" (server setting `backupPath`), or the server's `<root>/backups` when blank (`window/Backup.js`). The `miharchy-` prefix keeps the sync from reading it as a phone backup; the `backup-` part keeps the sync's pruning off it. The include rows are Suwayomi's `autoBackupInclude*` settings, shared with its automatic backups. Server settings never go in, and client data never goes in either, whatever `autoBackupIncludeClientData` says, the same as the sync's export (`backupFlags` in `Desktop.kt`). The backup folder never is the sync folder: Settings refuses either way round, and the helper refuses too, because Suwayomi's own `org.suwayomi.tachidesk.auto*` backups there would read as phone backups. Both compare the paths after Java's `Path.normalize()` (`backupRefusal` in `Main.kt`, `normalizePath` in `Settings.js`), give the same message, and read their cases from `sync/src/test/resources/backup-folder-cases.json`; Settings saves the normalized path, and only once the folder exists ("<folder> is not a folder.", the helper's other refusal). A backup folder inside the sync folder passes both. Saving the backup folder also sends `autoBackupIncludeServerSettings: false`.
- Automatic backups are Suwayomi's schedule, not a Miharchy timer: Settings sets `backupInterval` (days, 0 off), `backupTime` (HH:MM) and `backupTTL` (days to keep, 0 forever). Suwayomi deletes by age and only its own `org.suwayomi.tachidesk.auto*` names, so Mihon's "number of backups" becomes an age here.
- Baselines and the lock file `sync.lock` live in `~/.local/share/miharchy/sync/` (mode 700). The helper holds the lock for its whole run; a second sync, from the popup or the window, exits with "A sync is already running." The OS drops the lock when the process ends, even on a crash.
- Each sync merges the phone backup's and the phone baseline's `backupSources` (source id → name) into meta `miharchy.sourceNames`. Suwayomi gives a manga whose source is not installed `source: null` and cannot fetch its cover, so the window names the source from that meta and shows the placeholder cover (`Cover.qml`) without asking for the image.
- `gap` in `Export.kt` measures the newest phone backup against a desktop backup and returns two lists of `PhoneChange`: `restorable`, what a stock Mihon restore brings (added to the library, categories changed, marked read, bookmarked, last page raised, track added, chapters read raised), and `byHand`, what it cannot apply, because Mihon's restore keeps `favorite`, `read` and `bookmark` with OR, `lastPageRead` with max, and replaces categories only with a non-empty list. It never deletes a track and only raises chapters read on one the phone has. A manga the restore adds brings its notes. After a sync, the summary's `unreachable` is `byHand` against the backup just written. A change stays listed until a later phone backup shows it.
- Notes on a manga (Mihon's notes, Markdown) are manga meta `miharchy.notes`: `n` writes them, the manga screen renders them. Suwayomi's backup has no notes field, so the sync maps them itself: `SetNotes` brings a phone change in, and `forMihon` writes each library manga's notes into the export. Mihon's restore keeps the notes of a manga the phone already has (`RestoreRepositoryImpl.mergeManga`), so a desktop edit to such a manga stays in the "repeat on the phone" list as "notes changed".
- The sync brings the phone's tracks into Suwayomi's database (ADR 0002, track merge rules). It never calls a tracker: no `updateTrack` or `bindTrack` (both push), only the restore and `unbindTrack` with `deleteRemoteTrack: false`.
- A sync starts from `s` in the window, `s` in the popup, or, with the Settings row "Sync when a phone backup arrives" on (meta `miharchy.autoSync`), from the mark when a new phone backup lands in the sync folder (`docs/agents/plugin.md`). There is no timer and no sync without the shell.
- `window/Sync.js` runs the helper for both the window (`SyncView.qml`, `s` on Library and Updates, or the palette) and the popup (`s`). It runs the installed helper `~/.local/share/miharchy/helper/bin/miharchy-sync` (`Setup.HELPER_DIR`) first, then a dev checkout's `sync/build/install/miharchy-sync/bin/miharchy-sync` beside `window/` and `plugin/`.
