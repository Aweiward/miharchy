# Sync, backups and restore

The Kotlin library in `sync/` (merge rules, Mihon backup classes, export, health), which miharchy-core runs as routes (`core/README.md`), and the window code that calls them (`Sync.js`, `Backup.js`, `Restore.js`).

- `sync.run { folder?, dryRun?, apply? }` is the whole sync in one call (`Sync.corePayload`). Without `folder` it reads meta `miharchy.syncFolder`, so the window and the popup start it the same way. It merges the newest phone backup in (none yet is fine), writes the desktop backup to the sync folder, and only then moves both baselines. A failure leaves the baselines alone, so the next sync retries.
- The merge reads a manga missing from the phone backup as removed and a missing chapter as unread, so an empty or partial backup (a fresh Mihon, another phone, chapters left out) reads as mass removal. The sync holds when the changes remove at least 5 manga that are also at least 10% of the desktop library, or mark at least 50 chapters unread (`holds` in `Merge.kt`). A held sync returns `held: true` before `apply`, the export and both baseline writes, like `dryRun`; `apply: true` runs it anyway. The window lists the changes and sends `apply: true` on `y` (`sync-held` scope); the popup only says "Sync held" and never applies.
- Before a real sync moves the desktop baseline, it copies the old one to `pre-sync.tachibk` beside it (mode 600). "Undo the last sync" (palette) opens "Restore a backup" on that file. A sync overrides a desktop value only while it still equals the desktop baseline (`pick` and the `inLibrary` rule in `Merge.kt`), so that baseline holds everything a sync can remove, and the restore only adds.
- `backup.check { file }` names the sources and trackers a backup needs and core lacks (`Restore.checkPayload`). `backup.import { file }` restores the whole file, without client data or server settings, and merges the file's source names into meta `miharchy.sourceNames` (`Restore.importPayload`). Core runs one of `sync.run`, `backup.export` and `backup.import` at a time, so a restore never overlaps a sync. It moves no baseline: the restore only changes the desktop library, so the next sync counts those changes as desktop changes (ADR 0002) and keeps them. The window's "Restore a backup" (`window/Restore.js`, `RestoreView.qml`, palette only) sends both.
- Backups Miharchy writes to the sync folder are named `miharchy-<UTC yyyy-MM-dd_HH-mm-ss>.tachibk`, so names sort by time. The sync ignores them when it picks the phone backup (the newest other `.tachibk`). It writes through a temp file that does not end in `.tachibk`, then renames it, and keeps the newest three (only names of exactly that shape count). The backup leaves out the Default category, client data and server settings. Stock Mihon restored a `miharchy-*.tachibk` export of a real 216-manga library without issues (the user's phone, 2026-10-04).
- Each desktop backup a sync writes carries the app preference `miharchy_backup` (`MARKER_KEY`), its own file name (ADR 0006). Mihon restores app preferences unfiltered and backs them up by default, so `restoredFrom` reads the last desktop backup the phone restored from the newest phone backup. "Create a backup" carries no marker. 
- **Sync health in the window.** `window/Sync.js` reads the `sync.health` reply (`healthReply`) and words it: `healthSummary` for the Settings row "Phone sync" (an action row under "Sync when a phone backup arrives", command `sync.health`, also in the palette), short enough for the row; `healthLines` for the panel Enter opens (`SyncView` in mode `health`: what a restore brings under "In Mihon, restore <newest desktop backup>", the by-hand list in red under "Repeat them in Mihon", and the app-settings hint when `markerMissing`); `healthPopupLine` for the popup. The "restore pending" count comes from `restorable`, never from `pendingSince`, which stays set until the next sync. `SyncView` owns the health state: it reads it when the Settings view shows (`healthWanted`), on `sync.health`, and after each sync; `SettingsView` shows it through its `health` property.
- **Sync health.** A sync stores `pending-since` in the state dir: the time of the first sync whose `restorable` list went from empty to non-empty, cleared when it is empty again (`pendingSince` in `Health.kt`). A sync also restarts it when the newest phone backup lacks nothing of the last desktop backup (`caughtUp`): the phone caught up between two syncs, so the phone backups since then do not count toward a new change. The phone is **behind** when `restorable` is not empty and at least 3 phone backups (`BEHIND_AFTER`; Mihon keeps 4) are newer than pending since. A phone backup's time comes from Mihon's name, `app.mihon_<local yyyy-MM-dd_HH-mm>.tachibk`, read in the desktop's time zone, else from its file time (`phoneBackupTime`). `sync.health { folder? }` answers with every field: `phoneBackup`, `phoneBackupAt`, `desktopBackup`, `restored`, `markerMissing` (the phone backup has no app preferences at all, so no marker can come back), `restorable`, `byHand`, `pendingSince`, `behind`. It reads the newest phone backup, the newest desktop backup and `pending-since`, writes nothing and takes no lock. No phone backup or no desktop backup is a valid answer.
- "Create a backup" (palette, or its Settings row) sends `backup.export` (`Backup.PAYLOAD`). It writes `miharchy-backup-<UTC>.tachibk` to the backup folder: Settings' "Backup folder" (server setting `backupPath`), or `<core data>/backups` when blank. The `miharchy-` prefix keeps the sync from reading it as a phone backup; the `backup-` part keeps the sync's pruning off it. The include rows are the `autoBackupInclude*` settings, shared with the automatic backups. Server settings never go in, and client data never goes in either, whatever `autoBackupIncludeClientData` says, the same as the sync's export. The backup folder never is the sync folder: Settings refuses either way round, and core refuses too. Both compare the paths after Java's `Path.normalize()` (`backupRefusal` in `sync/.../State.kt`, `normalizePath` in `Settings.js`), give the same message, and read their cases from `sync/src/test/resources/backup-folder-cases.json`; Settings saves the normalized path, and only once the folder exists ("<folder> is not a folder.", core's other refusal). A backup folder inside the sync folder passes both. Saving the backup folder also sends `autoBackupIncludeServerSettings: false`.
- Automatic backups run on core's timer (`Backups.kt`, `core/README.md`, #375), so they run while the window is closed. Settings sets `backupInterval` (days, 0 off), `backupTime` (HH:MM) and `backupTTL` (days to keep, 0 forever), so Mihon's "number of backups" becomes an age here. Core writes `miharchy-auto-<UTC>.tachibk` into the backup folder, or `<core data>/backups` when the row is blank, and deletes only those files by age.
- Baselines, `pre-sync.tachibk` and `pending-since` live in `sync/` inside core's data folder, which is mode 700. A second sync, from the popup or the window, while one runs is refused with "A sync is already running." Setup's move copies an old helper's baselines from `~/.local/share/miharchy/sync/` once, where core has none.
- Each sync merges the phone backup's and the phone baseline's `backupSources` (source id → name) into meta `miharchy.sourceNames`. Core gives a manga whose source is not installed `source: null` and cannot fetch its cover, so the window names the source from that meta and shows the placeholder cover (`Cover.qml`) without asking for the image.
- `gap` in `Export.kt` measures the newest phone backup against a desktop backup and returns two lists of `PhoneChange`: `restorable`, what a stock Mihon restore brings (added to the library, categories changed, marked read, bookmarked, last page raised, track added, chapters read raised), and `byHand`, what it cannot apply, because Mihon's restore keeps `favorite`, `read` and `bookmark` with OR, `lastPageRead` with max, and replaces categories only with a non-empty list. It never deletes a track and only raises chapters read on one the phone has. A manga the restore adds brings its notes. After a sync, the summary's `unreachable` is `byHand` against the backup just written. A change stays listed until a later phone backup shows it.
- Notes on a manga (Mihon's notes, Markdown) are manga meta `miharchy.notes`: `n` writes them, the manga screen renders them. `sync/`'s backup classes have no notes field, so the sync maps them itself: `SetNotes` brings a phone change in, and `forMihon` writes each library manga's notes into the export. Mihon's restore keeps the notes of a manga the phone already has (`RestoreRepositoryImpl.mergeManga`), so a desktop edit to such a manga stays in the "repeat on the phone" list as "notes changed".
- The sync brings the phone's tracks into core's database (ADR 0002, track merge rules). It never calls a tracker: `Sync` in core holds no tracker client.
- A sync starts from `s` in the window, `s` in the popup, or, with the Settings row "Sync when a phone backup arrives" on (meta `miharchy.autoSync`), from the mark when a new phone backup lands in the sync folder (`docs/agents/plugin.md`). There is no timer and no sync without the shell.
- **Build downloads are verified.** The wrapper checks the Gradle zip against `distributionSha256Sum` in `sync/gradle/wrapper/gradle-wrapper.properties`. Gradle checks every dependency and plugin against `sync/gradle/verification-metadata.xml`, so a changed hash fails the build. CI validates `gradle-wrapper.jar` (`gradle/actions/wrapper-validation`, pinned to a commit). After a dependency, plugin or Gradle version change:
  1. For a new Gradle version, run `./gradlew wrapper --gradle-version <v> --gradle-distribution-sha256-sum <hash>`, with the hash from `https://services.gradle.org/distributions/gradle-<v>-bin.zip.sha256`.
  2. Delete `verification-metadata.xml`, because Gradle adds entries and never removes unused ones.
  3. Run `./gradlew --write-verification-metadata sha256 test` in `sync/` with a scratch `GRADLE_USER_HOME`, so every artifact downloads fresh.
  4. Check a new jar's hash against Maven Central's `.sha256` file beside it. Commit the metadata with the change.
- Core's tests (`core/server/src/test/kotlin/miharchy/core/SyncTest.kt`) run every `MergeTest` case through core's database, so a change in `sync/` is tested in both. A change in `sync/` also changes Setup's core fingerprint, so installed cores show "outdated" until Setup rebuilds them.
